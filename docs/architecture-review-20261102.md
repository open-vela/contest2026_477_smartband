# MoonCat 架构与性能审查（2026-11-02）

> 本文保留最初审查现场。后续修复、实机数据和当前待办见 [架构修复记录](architecture-fixes-20261102.md)，以该记录为准。

审查基线为 `e728d44`，覆盖 UI/LCD、应用状态、通知桥、运动持久化、天气和网络同步。板端通过 ADB 5038/1234 读取状态，远端仅使用 `/data/mooncat-closure-build05`。本轮源代码改动尚未烧录；已部署的六动作帧率结果属于上一轮固件。

## 结论与优先次序

最值得继续开发的是 **ILI9341 矩形传输、离线计时及独立提醒调度、UI 存储解耦**。目前不宜把“六个局部动画接近 60 FPS”扩展成全系统或全屏 60 FPS。

| 优先级 | 发现及证据 | 建议与验证方式 |
|---|---|---|
| 高 | ILI9341 没有 `putarea`，`lcd_dev.c` 将矩形逐行转成 `putrun`；每行重新选择窗口并发送 MEMORY_WRITE | 添加矩形写入，紧密行跨度可批量发送，带 padding 的行必须跳过填充。验证窗口边界、横屏方向、RGB565 字节序、传输长度、失败返回，再做同场景板端对比 |
| 高 | 本轮板端 `date` 为 `Thu, Jan 01 08:18:42 1970`；`wall_now()` 拒绝 2020 年以前的时间，初始化及所有提醒接口因此返回 `clock_changed` | 分离单调时钟与可信日历：相对提醒/恢复计时使用 monotonic，今日暂停/跨重启任务使用可信 calendar；明确离线启动和重启恢复策略 |
| 高 | `mooncat_app_poll()` 由 LVGL 的 1 秒回调驱动；命令、ACK_SHOWN 与 tick 可能持锁执行 `fflush/fsync/rename` | 单独的应用服务工作线程拥有状态机和存储。UI 发有界命令，读取快照及完成事件；保留落盘成功后才报告成功、revision、去重及队列满语义 |
| 中 | 旧 Agent 通知桥仅一个 `g_pending_message`，后来的消息释放前一条；新任务表不经过此单槽 | 为旧通知提供有界 FIFO、阅读停留时间和明确溢出策略。不能只换队列却仍每 100 ms 覆盖卡片；也不能将 bus push 宣称为用户已看见 |
| 中 | 同步线程先 drain 健康队列，再逐项持久化，失败只记日志；满队列丢最旧样本 | 持久化成功后再移除待处理事件，设置重试退避、容量上限与丢弃计数。定义 at-least-once 与事件 ID 去重，避免简单回插造成重复或重排 |
| 中 | 远程截图仅调用 `lv_snapshot_take(lv_screen_active())`；COACH 卡片位于 `lv_layer_top()` | 截图需覆盖 active/top/system 层，正确处理 alpha、stride 与层次；用板上真实卡片校验。当前截图缺卡片不能证明提醒没有显示 |

## 已有架构中应保留的部分

- Agent 回调通过数据桥接交给 UI，未在回调中直接调用 LVGL。
- 应用状态机有 8 个任务槽、revision、幂等与过期检查；存储失败不提交新内存状态。异步改造应保留这些语义。
- 网络同步已经有独立 pthread、条件变量、连接/请求超时、重试退避与 DNS 恢复，不是 UI 内执行所有网络请求。
- 运动数据回调在页面不可见且无活动运动时直接返回；天气按 revision 更新，音乐文本/图片也做了变化检查。不能仅根据定时器频率认定这些模块持续重绘。
- 帧缓存有 2 MiB/64 项上限和分配失败回退，不需要为了缓存复制所有动画资源或新增远端构建目录。

## 图形路径的具体证据

当前调用关系：

```mermaid
flowchart LR
    UI[LVGL UI 线程] --> Draw[局部渲染缓冲 120 行]
    Draw --> Flush[LCDDEVIO_PUTAREA 同步调用]
    Flush --> Fallback[lcd_dev 逐行回退]
    Fallback --> Run[ili9341_putrun]
    Run --> Window[每行设置列窗口和页窗口]
    Window --> SPI[MEMORY_WRITE 与 SPI 像素传输]
    SPI --> Ready[返回后 flush_ready]
```

远端实际参与链接的源文件：

- `nuttx/drivers/lcd/lcd_dev.c:253-283`：有 `putarea` 才走矩形路径，否则逐行 `putrun`。
- `nuttx/drivers/lcd/ili9341.c:537-555,579-616,844`：每行配置窗口、写命令和数据；planeinfo 只设置 `putrun`。
- `vendor/allwinnertech/chips/r528/drivers/rtos-hal/hal/source/disp2/soc/ili9341_lcd_spi.c:425-487`：RGB565 字节序转换后调用 `hal_spi_write`，使用已有整屏大小的中转缓冲。
- `nuttx/.config`：ILI9341、硬件 SPI、横屏、RGB565 均启用；`nuttx.map` 包含 `ili9341_lcd_spi.o`。

120 行刷新重复 120 组窗口/写命令。一次 `putrun` 内有 2 次窗口命令、8 次参数和1次写命令，硬件 SPI 路径逐个发送这些单字节，再发送像素。矩形传输有机会去掉大量小传输开销；**本轮尚未实现或测出其提速幅度**。

既有板端计数见 `docs/evidence/finals-animation-20261102/`：

| 场景 | 像素混合平均 | render 区间平均 | 单次 PUTAREA 平均 |
|---|---:|---:|---:|
| paced-cat | 10.81 µs | 8.81 ms | 6.71 ms |
| carousel-paced-window | 70.62 µs | 13.54 ms | 8.71 ms |

这些指标各有自己的计数分母，不能直接相减或当作全屏单帧分解。轮播窗口有滑动、停留和不同脏区，49.15 render FPS 不是纯转场 FPS。计数时钟粒度、软件提交与面板实际扫描也不同。

ILI9341 子驱动当前忽略 `hal_spi_write()` 的返回值并返回 OK，通用 `putrun` 也不传播 `sendgram` 结果。因此上一轮“无新增 ioctl 错误”只证明接口统计为零，不证明所有底层 SPI 传输都没有错误。做矩形接口时应同时贯通错误返回。

仅添加第二块 LVGL 缓冲不会自动获得渲染/传输重叠：当前 flush 同步阻塞。应先消除逐行命令，再分别测传输与等待开销，决定是否需要异步 DMA 和缓冲所有权协议。RGB565 全屏 320×240×60 Hz 的像素净带宽为 **73.728 Mbit/s**，尚未计算协议开销；局部动画达标不等于全屏可达标。当前实际 SPI 时钟未测量。

## 本轮已实现的两项改进

### 空闲状态不再定期写闪存

`agent/mooncat_app_service.c` 原先忽略 `last_now/focus_seconds` 后，每超过 60 秒仍保存一次；有效时钟下，完全空闲的一天会产生约 1440 次额外状态文件写入和 fsync。

现在无业务状态及累计专注时间变化时不写；专注计数仍按 60 秒检查点保存。任务到期、偏好变更和时钟回退立即保存。仍保留先持久化、后提交内存的失败语义，没有删除 fsync。时钟回退与最新内存时间比较，覆盖回退后仍晚于上次落盘时间的情况。

真实 C 服务测试注入时钟与 fsync 故障，覆盖：24 小时逐秒空闲 0 次额外 fsync；59/60 秒计数边界；检查点失败后同一秒重试；任务到期保存失败不提交；关闭专注与偏好即时保存；回拨；重启恢复。这里是主机文件系统测试，不是 NAND 寿命或断电实测。

### 调试控制按活动状态轮询

`openvela_ui_remote.c` 空闲轮询从 20 ms 改为 250 ms，即名义 50 次/秒降至4次/秒（减少92%），触摸手势期间仍为20 ms。代价是新调试命令等待下次轮询最多约250 ms，另加 UI 调度延迟；不改变物理触摸采样通道。

真实控制源码 harness 验证空闲5秒20次回调、手势中点/释放、忙碌拒绝、错误命令、截图 stride 和清理。没有据此宣称整机 CPU 或功耗下降92%。

主机全套回归为 **43 passed**，针对性回归为 **16 passed**。hushen 原目录增量编译退出码0，`vela.bin` 为7,716,352字节；两个源文件与本地一致，最终链接使用本轮重新编译的归档对象，归档成员内容与对应对象逐字节一致。构建存在原厂 NAND 等代码警告，并非无警告构建。测试日志与编译核对记录位于 `docs/evidence/architecture-20261102/`；本轮未烧录，不能宣称这两项改动已经在板上验证。

## 下一轮开发顺序

1. 为 ILI9341 增加矩形写入与错误传播，先测 stride/padding、奇数宽度、边界和异常传输，再复用现有后台更新工具做板端对照。保持驱动及资源单份构建。
2. 明确离线提醒的时间模型，配合应用服务工作线程迁移；用有效时钟、活动提醒和保存同时运行的负载测 UI 最长阻塞及帧间隔分布。
3. 完善通知 FIFO、同步持久化重试与截图层覆盖，以便可靠验证“收到→显示→确认→落盘”。
4. 再测健康页、运动页、转场和音乐并发。按 p95/p99 帧间隔、最长卡顿、队列深度、失败/丢弃数与堆峰值评估全系统，平均 FPS 仅为其中一项。

另有 LCD 初始化分配失败清理、GETAREAALIGN 失败默认值、同步线程退出后的运行状态等健壮性问题，尚未做故障注入或修改。运动持久化也仍处于 UI 调用链，应随存储工作线程迁移；它有 dirty 检查，不能误报为每250 ms固定落盘。
